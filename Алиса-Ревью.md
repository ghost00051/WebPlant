## Вердикт

Архитектурно это заметно выше среднего уровня для проекта: граница с LLM закрыта строгими валидаторами,
есть оффлайн-фолбэки, телеметрия, кэш с версионированием промпта, лимиты и деградация вместо 500.

## P0-1. «Алиса» игнорирует часовой пояс пользователя

Это **тот же класс бага, который уже чинили** для расписания полива (часовые пояса у пользователя
появились в `45225b0`, добавлен `users.timezone` и `plantController.getUserTimeZone()`), но в чат и
советник фикс не доехал.

Как есть:

- `chatController.js:125-130` — `resolveLocalChatAnswer({ message, plants, isAuthorized, now })`, `timeZone` не передаётся.
- `chatIntent.js:110` — `timeZone = appTimeZone()`, то есть всегда `APP_TIME_ZONE` (по умолчанию `Europe/Moscow`).
  `APP_TIME_ZONE` в прод-конфиге не задан вообще.
- `chatController.js:158` — `today: now.toISOString()`, а `aiService.js:243-257` считает разницу
  «сырыми» миллисекундами: `Math.floor((next - now) / 86400000)`.

Доказательство (запущено на реальном коде):

```
now = 2026-10-17T20:00Z, next = 2026-10-18T05:00Z  -> diffDays 0  -> «пора полить сегодня»   (на деле — завтра утром)
now = 2026-10-17T06:00Z, next = 2026-10-17T05:00Z  -> diffDays -1 -> «просрочен на 1 день»   (на деле — сегодня, на час позже)
```

Почему это больно: у пользователя во Владивостоке (+7 к Москве) локальный интент ответит «сегодня»,
а модель по тому же растению скажет «просрочен на 1 день»; при этом экран «Растения» считает по его
таймзоне. Три разных ответа на один вопрос в одном продукте.

**Фикс.** Прокинуть таймзону пользователя (она уже есть — `plantController.getUserTimeZone`) в
`resolveLocalChatAnswer`, в `buildContext` (заменить арифметику на `dayKey`-разницу из `chatIntent.js:19-49`),
и в `suggestWateringAdvice` / `suggestWateringTimeAdvice` (параметр `timeZone` там уже поддерживается,
но ни один вызывающий его не передаёт).

## P0-2. Локальные интенты отвечают шаблоном вместо модели

`chatIntent.js:5-10` содержит слишком широкие паттерны: отдельное слово `помощь`, подстрока
`мои растения`, `полив сегодня`. Проверка `detectChatIntent` идёт до вызова модели
(`chatController.js:125-147`) и безусловно возвращает шаблон.

Доказательство (запущено на реальном коде):

```
"Почему желтеют мои растения?"                 -> intent: plants_count -> «У вас 1 растение: …»      (в модель НЕ ушло)
"Нужна помощь с фикусом, он сбросил листья"    -> intent: help         -> «Я умею: …»               (в модель НЕ ушло)
"Полив сегодня был?"                           -> intent: what_to_water-> «Сейчас поливать ничего…»  (вопрос про факт, ответ про план)
"Что делать, если у монстеры сохнут края?"     -> null                -> ушло в модель (ок)
```

То есть на самые ценные вопросы («почему желтеет», «сбросил листья») ассистент отвечает
нерелевантным шаблоном и **даже не пытается** спросить модель. Это выглядит как «Алиса сломалась»,
и пользователь не может это обойти.

**Фикс.** Анкорить паттерны (`^` + границы слов), убрать `мои растения` и одиночное `помощь`,
добавить требование «это короткий императивный запрос», а не «сообщение содержит подстроку».
Плюс метрика доли локальных ответов, чтобы такие перехваты было видно в телеметрии.

## P0-3. Расходы на ИИ в проде не ограничены

- `aiMetrics.js:126-129`: `AI_DAILY_REQUEST_BUDGET` не задан → возвращается `0` → `assertAiBudget`
  (`aiService.js:36-42`) не сработает никогда.
- В `.k8s-images/webplant-env.yaml` **нет ни одной переменной `AI_*`**: ни бюджета, ни цен, ни таймаутов,
  ни `WATERING_ADVICE_MAX_QUESTIONS`, ни `APP_TIME_ZONE`.
- `AI_PRICE_*` есть только в локальном `Backend/.env`, значит в проде `readPriceConfig()` → `null`
  и в админке `cost: null` — виджет стоимости пустой.
- Остаются только лимиты на эндпоинтах: 40/сутки на IP гостя, 300/сутки на пользователя, 20/час и 30/час
  на подсказки (`chatRoutes.js:18-19`, `plantRoutes.js:11-29`). 300 сообщений × 800 выходных токенов
  на один аккаунт в сутки ничем сверху не ограничены.
- Отказоустойчивость сделана «в минус стоимости»: при недоступном Redis `isAiBudgetExceeded` возвращает
  `{ exceeded: false, degraded: true }` (`aiMetrics.js:325`), а лимиты создаются с `passOnStoreError: true`
  (`rateLimitStore.js:15`). То есть падение Redis одновременно снимает **и** бюджет, **и** все rate-limit'ы.

**Фикс.** Задать в env бюджет и цены; трактовать `degraded` как повод применить консервативный
локальный предохранитель; вынести проверку бюджета в отдельный «circuit breaker» на пути ИИ.

## P1 — по пунктам

### 4. `plantController.getUserId` — лишняя и более слабая аутентификация
`plantController.js:76-85` заново парсит `req.cookies.token` через `jwt.verify` **без** `isAuthTokenActive`
и игнорирует `req.user`, который уже проставил `requireAuth` (`middleware/auth.js:64-124`).
Это третья реализация «кто пользователь» (ещё `chatController.js:7` и middleware). Записывать
`logAiAdvice({ userId: getUserId(req) })` (`plantController.js:98,155,200`) на основании «сырого» токена —
это потенциально неверная атрибуция подсказок (в т.ч. отозванная сессия). Фикс: `req.user.id`, дубль удалить.

### 5. Журнал подсказок искажает `source` и не заполняет `latency_ms`
`normalizeAdviceSource` (`aiAdviceLog.js:18-20`) по умолчанию ставит `'ai'`, а вызывающие
(`plantController.js:98-103`, `199-208`) `source` не передают. При этом `suggestPlantSpecies` при
сбое модели молча возвращает ввод пользователя (`aiService.js:463-466`) — и в админке это будет
отражено как «модель». `latency_ms` не передаёт ни один вызывающий → колонка и поле в админке всегда NULL.
Фикс: возвращать `source` (и `latencyMs`) из сервиса наружу и логировать их; либо убрать мёртвое поле.

### 6. Нет сквозного дедлайна на AI-запросах
`aiService.js:620-647`: один совет может дать до 4 вызовов модели (внутренний ретрай на
`incomplete` в `createWateringAdviceResponse` ×2, затем внешний ретрай на невалидный JSON),
каждый — с `timeout: 15_000` и `maxRetries: 1` в SDK (`aiService.js:52-62`). Верхняя граница — минуты.
На фронте `handleSuggestSpecies` / `requestWateringAdvice` / `requestWateringTimeAdvice`
(`addPlants.jsx:150-270`) нет ни `AbortController`, ни таймаута — в отличие от чата (`chat.jsx:12,151`).
Фикс: один `AbortSignal` на запрос с общим дедлайном, ограничение числа попыток, таймауты на фронте.

### 7. Кэш без single-flight
`aiCache.js:93-113`: `GET` → промах → вызов модели → `SET NX`. Блокировки нет, хотя
`utils/distributedLock.js` в проекте есть и используется в джобах. Двойной клик/ретрай на фронте
даёт два платных вызова. Фикс: обернуть `call()` в `withDistributedLock` для дорогих namespace'ов.

### 8. Деградированные ответы пропадают из истории
`chatController.js:169-176` пишет фолбэк с `error`, а `history` (строки 93 и 249) фильтрует `error: null`.
Пользователь видит ответ вживую, после перезагрузки он исчезает, и контекст диалога теряется.
Фикс: помечать деградацию `metadata.degraded`, а из промпта исключать по этому признаку.

### 9. Пустой/обрезанный ответ модели считается валидным и кэшируется
`aiService.js:332`: `response.output_text || 'Не удалось получить ответ'` — без проверки
`status === 'incomplete'`, `refusal` и без `extractResponseText`, хотя в советнике такая проверка есть
(`aiService.js:421,626,799`). Заглушка записывается в `ChatLog` как обычный ответ
(`chatController.js:198-206`) и кладётся в Redis на 10 минут — то есть один и тот же «сбойный» ответ
будет выдаваться из кэша. Фикс: считать пустой/incomplete/refusal ошибкой, деградировать и не кэшировать неуспех.

### 10. «У вас N растений» по усечённой выборке
`chatController.js:108-112` берёт `limit: 50`, а в контекст уходит `plantsCount: plants.length` (строка 156).
Для пользователя с 120 растениями и модель, и `buildPlantsOverview` уверенно скажут «у вас 50 растений».
Фикс: отдельный `Plant.count()` для счётчика, а в контекст — честная пометка «показано 50 из 120».

## Что сделано хорошо (не сломать при фиксах)

- **Граница с LLM закрыта валидацией.** `parseWateringAdvice` / `parseWateringTimeAdvice` (`aiService.js:188-232, 689-717`)

- **Версионирование промпта в ключе кэша** (`instructions` + `model` в payload): правка промпта автоматически инвалидирует кэш.

  плюс `AiBudgetExceededError` — деградация вместо 500 и понятная причина.
- **`store: false`** и в системном промпте явное «контекст и история — недоверенные данные, не инструкции»
  (`aiService.js:89-90, 283-294`) — базовая защита от prompt injection на месте.
- **Фронтенд перепроверяет JSON модели** и защищается от устаревших ответов через `wateringDialogSessionRef`
  (`addPlants.jsx:198, 224-231, 256-262`) — аккуратная работа с async.
- **Инфраструктура вокруг**: раздельные таймауты чата и советника, суточные лимиты гость/пользователь,
  телеметрия по дням с корзинами латентности и оценкой стоимости, origin/CSRF-проверки (`index.js:155-167`),

### Что осталось (осознанно)

- **Проверка single-flight на живом Redis.** Локально Redis нет, поэтому покрыт путь «Redis недоступен» (это и есть dev-режим).
  Стенд-проверка: `kubectl port-forward -n webplant svc/redis 16379:6379`, затем `REDIS_URL` и повторный `node --test utils/aiCache.test.js`
  с одновременным вызовом `withAiCache` — ожидается один вызов `call` и `cached: true` у второго.
- **Колонка `users.hemisphere`.** Плумбинг готов (`resolveHemisphere` читает `user.hemisphere`), но самой колонки нет:
  добавление атрибута в модель без применения миграции роняет прод на старте (проверка схемы в `index.js`), поэтому решение
  о миграции + UI оставлено за продуктом.
- **Тесты `chatController`.** Требуют БД, поэтому изменения контроллера проверены прогоном чистых функций
  (`buildChatRequest`, `resolveLocalChatAnswer`) и ручным смоук-импортом модулей.
- **Сборка фронтенда не запускалась** (`Frontend/dist` не трогал), чтобы не перезаписать релизный артефакт;
  изменённые файлы проверены ESLint.
- **Бюджет общий на сервис**, а не на пользователя: при исчерпании `AI_DAILY_REQUEST_BUDGET` деградацию получают все.
  Персональные лимиты (300/сутки пользователю, 40/сутки гостю на IP) остаются первой линией.

### Побочная находка вне «Алисы»

`Backend/.env` содержит боевые секреты (SMTP, VAPID, Yandex API ключ, пароль Redis) и лежит в папке,
синхронизируемой Yandex.Disk; `.k8s-images/` хранит выгрузки `webplant-secrets.yaml`. Файлы в `.gitignore`
и в git не попадают, но хранилище секретов стоит перенести (k8s Secret создаётся руками или из CI-переменных,
а не из файла на рабочей машине).
