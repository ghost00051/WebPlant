# Git-хуки WebPlant

Хуки версионируются вместе с проектом: источник — этот каталог, установщик копирует файлы
в `$GIT_DIR/hooks` (в этом репозитории — `C:\WebPlant.git\hooks`).

```bash
node scripts/install-git-hooks.mjs             # установить/обновить хуки (после правок и pull)
node scripts/install-git-hooks.mjs --status    # сравнить копии с источником (код 1 при расхождении)
node scripts/install-git-hooks.mjs --uninstall # удалить установленные копии
```

Почему копирование, а не `core.hooksPath` на `.githooks`: рабочая копия лежит в папке
Yandex.Disk, где файл может перезаписать синхронизация — один раз так потерялась строка
`#!/bin/sh`, и git перестал запускать хук (`cannot spawn .githooks/pre-push`). Установленная
копия лежит рядом с git-каталогом, вне синхронизации; расхождение с источником показывает
`--status`, а незакоммиченные правки в источнике видно через `git status`.

## pre-push: автотег версии

При `git push` хук берёт поле `version` из `Frontend/package.json` **отправляемого коммита**
(не из рабочего каталога — чтобы тег соответствовал именно тем файлам, которые уходят в remote)
и гарантирует, что этот коммит помечен тегом `v<version>`:

| Ситуация | Действие |
| --- | --- |
| тега `v<version>` нет | создаётся аннотированный тег (`git tag -a v1.2.13 -m "Версия 1.2.13"`) на отправляемый коммит и уходит в тот же remote |
| тег стоит точно на отправляемом коммите, но его нет в remote | тег досылается |
| тег уже указывает на более ранний коммит той же ветки | ничего: версия уже выпущена, тег не переносится и не дублируется |
| тег указывает на коммит из другой/расходящейся истории | предупреждение с подсказкой поднять `version`; существующий тег **не** переносится |
| `version` не semver или файла нет | предупреждение; push по умолчанию проходит |

Тег ставится только когда push затрагивает ветку, на которой стоит `HEAD`; push тегов,
удаление веток и push «чужой» ветки ничего не тегируют.

Соответствие «версия = тег» обеспечивается тем, что имя тега берётся из `package.json`
отправляемого коммита: пока `version` не поднята и не закоммичена, нового тега не появится.
Тег отправляется вложенным `git push --no-verify` (флаг исключает повторный вызов хука).

Например, если в последнем коммите `version` = `1.2.12`, первый push создаст тег `v1.2.12`;
после коммита с `1.2.13` следующий push создаст `v1.2.13`.

### Переменные окружения

| Переменная | Смысл |
| --- | --- |
| `WEBPLANT_SKIP_AUTOTAG=1` | разово пропустить автотег (push пройдёт как обычно) |
| `WEBPLANT_AUTOTAG_STRICT=1` | отменять push, если тег не удалось создать или отправить |
| `WEBPLANT_VERSION_FILE=Backend/package.json` | взять версию из другого файла |
| `WEBPLANT_AUTOTAG_CHECK_REMOTE=1` | сверяться с remote даже для уже выпущенной версии и досылать потерянный тег |
| `WEBPLANT_AUTOTAG_VERBOSE=1` | подробный вывод (в том числе когда тег не нужен) |

По умолчанию ошибки тегирования не блокируют push: хук печатает предупреждение
`pre-push[autotag]: ...` и пропускает push. Тег можно отправить вручную:

```bash
git tag -a v1.2.13 -m "Версия 1.2.13"
git push origin refs/tags/v1.2.13
```

### Замечания

- Тег отправляется до завершения основного push, поэтому при отклонённом push
  (например, non-fast-forward) тег на remote может остаться; после успешного push ветки
  он будет указывать на уже доставленный коммит.
- Хуки исполняются через `sh` из Git for Windows, поэтому в `.gitattributes` для
  `.githooks/*` зафиксирован `eol=lf`. Для запуска на Linux/macOS нужно право выполнения:
  `git update-index --chmod=+x .githooks/pre-push`.
- Файл хука обязан начинаться со строки `#!/bin/sh`: без неё git на Windows пытается
  запустить файл напрямую и падает с `cannot spawn ... : Exec format error`. Если после
  синхронизации Yandex.Disk файл повреждён (обрезан, нет shebang), `--status` это покажет,
  а починить можно так: `git checkout -- .githooks/pre-push && node scripts/install-git-hooks.mjs`.
- После `git pull` и правок в `.githooks/` нужно повторить `node scripts/install-git-hooks.mjs`,
  иначе запускается старая копия (или запустите `--status`, чтобы увидеть расхождение).
- Альтернатива для тегирования на стороне GitHub (если push идёт не с этой машины) —
  workflow в `.github/workflows`, который по push создаёт тег через API. Сейчас в репозитории
  CI нет, поэтому выбран локальный хук.
