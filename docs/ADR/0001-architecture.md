# ADR 0001. Архитектура WebPlant: стек, cookie-сессии, отдельный origin админки, Redis-локи

* **Статус:** принято
* **Дата:** 2026-10-20 (зафиксировано по состоянию репозитория: Backend 1.2.6, Frontend 1.2.20)
* **Контекст аудита:** P2.7 (ADR/записи решений), B20.3/B20.4 (миграции и совместимость),
  B2.1 (контракт API), I4.4 (RPO/RTO), P3.2 (схема БД и API)

## 1. Контекст

Продукт «Лейка» — учёт комнатных растений с ИИ-помощником, push-уведомлениями и почтовыми
рассылки. Ограничения, которые определили решения:

* небольшая команда (фактически один владелец продукта) и ограниченный бюджет;
* хостинг — один Windows-сервер с Docker Desktop: сначала compose-стек, затем Kubernetes
  в том же Docker Desktop; статический фронт выкладывается по FTP отдельно от backend;
* фронт и API живут на разных доменах (`checktheplants.ru` и
  `server.checktheplants.ru`), админка — на третьем (`admin.checktheplants.ru`);
* нужны фоновые задачи (напоминания о поливе, утренняя сводка, советы, очистка,
  рассылки) без отдельного брокера очередей и без второго сервиса;
* данные — персональные (email, телефоны, фото, переписка), поэтому нужны отзыв сессий,
  аудит действий администратора и понятные сроки хранения;
* внешние зависимости: Yandex Cloud AI (совместимый с OpenAI API), SMTP, web-push.

## 2. Решения

### 2.1 Express 5 + Sequelize + PostgreSQL 16 как основа backend

**Решение.** Один процесс Node.js 22 с Express 5, ORM Sequelize 6 и PostgreSQL 16.
Схема описана моделями (`Backend/models/*.js`), изменения — SQL-файлами
(`Backend/migrations/*.sql`), применяемыми по имени.

**Почему.**

* реляционная модель предметной области очевидна (пользователь → растения → фото/поливы),
  нужны транзакции, `LOCK.UPDATE` и частичные/уникальные индексы (дедупликация уведомлений,
  `endpoint` push-подписок, `idempotency_key` рассылок);
* Sequelize уже даёт ассоциации, JSONB и миграцию схемы через `sync()` для локальной
  разработки; отдельный ORM-фреймворк миграций не нужен — SQL прозрачнее и проверяем
  (CI прогоняет миграции дважды на чистой базе и проверяет идемпотентность);
* production-старт **проверяет схему** (`queryInterface.showAllTables()` +
  `describeTable()`) и падает с подсказкой, какую миграцию применить — это дешёвая защита
  от «код уехал, миграция нет».

**Альтернативы.** Prisma/Drizzle (потребовали бы отдельного инструмента миграций и кодогена
и не дают такого же контроля над `LOCK.UPDATE` в Sequelize-стиле), MongoDB (нет
транзакционных гарантий по расписаниям и рассылкам в нужном объёме). Отдельный сервис
миграций (Flyway/Knex) отклонён как лишняя сущность для одного процесса.

### 2.2 Redis для кэша, лимитов и распределённых локов

**Решение.** Redis 7 используется для трёх задач: кэш ответов ИИ (`ctp:ai:*`), общий store
rate-limit (`ctp:rl:*`), распределённые локи фоновых задач и идемпотентность рассылок
(`ctp:lock:*`, `ctp:idem:*`). Все обращения терпимы к недоступности Redis: лок
деградирует в «выполнить локально», лимитеры — `passOnStoreError`, кэш просто не работает.

**Почему.** Отдельный брокер (RabbitMQ/Kafka) не нужен: задачи — периодические, объём
небольшой, а требование «одна задача на кластер» закрывается `SET NX PX` с продлением TTL
и снятием через Lua. Redis уже был нужен для лимитов и кэша, поэтому второй компонент не
вводится.

**Следствия и границы.** При недоступном Redis каждая реплика выполняет cron-задачу сама
(возможны дубли push при 2+ репликах), суточный бюджет ИИ считается локально в памяти
процесса. Локи не работают между двумя независимыми стеками (compose и k8s) с разными
Redis — этот сценарий описан в `Backend/k8s/README.md`.

### 2.3 Cookie-сессии вместо JWT в localStorage

**Решение.** Токены живут только в httpOnly-cookie: `token` (JWT `session` 24 ч либо
`access` 15 мин) и `refresh_token` (JWT `refresh` 30 дней при «запомнить меня»). В
PostgreSQL пишется `sha256(jti)` в `auth_sessions`, отзыв — `revoked_at`. Cookie выдаются
на `.checktheplants.ru` с `SameSite=None; Secure` (нужно из-за разных origin).
CSRF-токена нет: изменяющие запросы проверяются по `Origin` и `Sec-Fetch-Site`, плюс
CORS-allowlist и запрет изменяющих запросов с cookie без `Origin`.

**Почему.**

* `localStorage` доступен любому XSS-скрипту; httpOnly-cookie этого риска не создаёт;
* серверная запись сессий позволяет мгновенно отозвать все сессии (смена пароля,
  инцидент, ротация `SECRET_KEY`) — в проекте это обязательное требование;
* JWT остаётся полезен: подпись позволяет отклонить поддельный токен без запроса в БД,
  а запись в БД даёт отзыв — сочетание дешевле полноценного session-store.

**Альтернативы.** JWT в `localStorage` (хуже для XSS), серверные сессии в Redis без JWT
(потеря Redis = массовый разлогин; сейчас так не происходит, потому что сессии в
PostgreSQL), отдельный CSRF-токен (учитывая строгую проверку `Origin`, сочли избыточным;
при появлении форм без `Origin` решение нужно пересмотреть).

**Следствия.** Требуется корректная настройка `FRONTEND_URL`/`ADMIN_PANEL_ORIGIN` и
домена cookie; мобильные/сторонние клиенты обязаны поддерживать cookie.

### 2.4 Отдельный origin админки

**Решение.** Админка — статический сайт `Frontend/admin` на `admin.checktheplants.ru`,
без собственного backend, с cookie-сессией администратора и запросами к тому же API.
Доступ проверяется на сервере (`requireAdmin` → `role === 'ADMIN'`), панель закрыта от
индексации, CSP и `X-Frame-Options: DENY` заданы в `.htaccess`.

**Почему.** Разделение пользовательского и административного контуров: админку можно
выгружать и обновлять независимо от SPA, закрыть отдельным `.htaccess`/Basic-авторизацией
на хостинге, ограничить по IP, не смешивать с публичной статикой и её CDN-кэшем.
Статический сайт не требует сборки и Node.js на хостинге.

**Альтернативы.** Админка внутри SPA (общий бандл, общий CSP, риск, что ошибка в
пользовательском коде ломает админку; сложнее ограничить доступ), отдельный backend для
админки (дублирование авторизации и логики).

**Следствия.** Нужен `ADMIN_PANEL_ORIGIN` в CORS и осознанное расширение allowlist;
админ-API защищён только ролью — любые действия из панели должны проверяться на сервере
(и проверяются), плюс пишутся в `admin_audit_logs`.

### 2.5 Redis-локи для cron-задач

**Решение.** Все фоновые задачи выполняются внутри процесса backend, но каждая точка
входа обёрнута в `withDistributedLock` (ключи `job:*`, TTL продлевается, снятие — Lua
только своим токеном). Задачи: `job:reminder-tick`, `job:morning-summary-tick`,
`job:care-advice-tick`, `job:cleanup-expired`, `job:push-broadcast`, `job:mail-broadcast`.

**Почему.**

* горизонтальное масштабирование backend (реплики в Kubernetes) не должно приводить к
  дублям напоминаний и рассылок;
* отдельный worker-процесс/Deployment потребовал бы образа, деплоя и мониторинга второй
  сущности; при текущем объёме задач это неоправданно;
* лок на Redis дешевле и проще, чем advisory-локи PostgreSQL для периодических задач
  (и PostgreSQL остаётся без нагрузки от «пустых» тиков).

**Границы.** Лок не даёт «ровно один раз» при падении процесса между побочными эффектами
(поэтому уведомления дедуплицируются по `dedupe_key`, а рассылки — по `idempotency_key`);
при недоступном Redis лок деградирует; для двух независимых стеков нужен общий Redis.

### 2.6 ИИ через Yandex Cloud (OpenAI-совместимый API) с кэшем и фолбэком

**Решение.** `openai` SDK с `baseURL: https://ai.api.cloud.yandex.net/v1`, модели
`gpt://<folder>/<model>`; ответы кэшируются в Redis; на все вызовы — таймаут и сквозной
дедлайн, суточный бюджет, при сбое — ответ по данным приложения (`degraded: true`) или
`503` для гостя при исчерпанном бюджете.

**Почему.** Модель не должна быть точкой полного отказа: локальные интенты
(`utils/chatIntent.js`) отвечают на типовые вопросы (полив, список растений) без платного
вызова; кэш снижает расход; деградация сохраняет работоспособность продукта.

**Альтернатива.** Собственный inference — вне бюджета и компетенций проекта.

## 3. Последствия для эксплуатации

| Решение | Что это требует |
| --- | --- |
| Sequelize + SQL-миграции | миграции только forward-only и аддитивные; откат данных — из дампа; production-старт падает при расхождении схемы |
| Один процесс backend с cron | `BACKGROUND_JOBS_ENABLED=true`; при масштабировании — Redis-локи; при недоступном Redis возможны дубли |
| Cookie-сессии | строгий allowlist origin, домен cookie, проверка `Origin`; ротация `SECRET_KEY` = разлогин всех |
| Отдельный origin админки | `ADMIN_PANEL_ORIGIN`, CSP админки, аудит действий администратора |
| Redis как зависимость | деградация без кэша/локов/общих лимитов; мониторинг `/health` → `redis` |
| Yandex Cloud AI | ключ и квоты в `SECRETS.md`; бюджет и таймауты в конфигурации; метрики в админке |
| Kubernetes рядом с compose | общий трафик переключается nginx-конфигом; данные не должны писаться в два стека одновременно |

## 4. Что пересмотреть при изменении условий

* появление second writer (несколько инстансов backend, пишущих в одну БД, — уже сейчас
  требуют аккуратной работы с локами и транзакциями);
* рост нагрузки, при котором cron в процессе начнёт мешать HTTP → вынести worker;
* необходимость сторонних клиентов (мобильное приложение) → понадобится token-flow без
  cookie и явный CSRF/anti-replay;
* требования к «ровно один раз» для рассылок → очередь с at-least-once и подтверждениями;
* регулирование/аудит, требующие WORM-хранения журнала действий → вынести
  `admin_audit_logs` в отдельное хранилище (сейчас append-only в PostgreSQL, 365 дней).
