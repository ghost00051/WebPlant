# REVIEW-CHECKLIST.md — Definition of Ready/Done, ревью PR и календарь проверок

Документ закрывает аудит-пункты P2.5/P3.4 (DoR/DoD и чек-лист ревью), B20.6 и P3.4
(план регулярных проверок). Ответственный за выполнение календаря — **владелец продукта**
(роль). Результаты проверок фиксируются в трекере (дата, проверка, результат, найденные
проблемы, ссылка на задачи).

## 1. Definition of Ready (задача готова к работе)

- [ ] понятна цель и пользовательская ценность; есть acceptance-критерии
- [ ] определён затронутый контракт API (`docs/api/openapi.yaml`) и необходимость миграции
- [ ] понятно, нужны ли изменения в фоновых задачах, лимитах и уведомлениях
- [ ] определены данные и персональные данные, которые затрагиваются
      (`docs/DATA-RETENTION.md`), при необходимости — согласование с юристом
- [ ] определены секреты, если задача их добавляет (`SECRETS.md`)
- [ ] оценены риски и способ проверки (unit / integration / e2e / ручной смоук)
- [ ] для срочных правок указано, почему нельзя сделать планово

## 2. Definition of Done (задача завершена)

- [ ] код влит в основную ветку, CI зелёный (frontend, backend, security)
- [ ] unit-тесты добавлены/обновлены; при изменениях схемы — integration-тесты
      (`RUN_INTEGRATION=1 npm run test:integration`)
- [ ] миграция аддитивна и идемпотентна, применена в тестовой среде, описана в PR
- [ ] контракт API обновлён в `docs/api/openapi.yaml` (если менялись пути/поля/коды)
- [ ] `CHANGELOG.md`: запись в Unreleased (или в релизном разделе)
- [ ] документация обновлена (`README`, `ARCHITECTURE`, `RUNBOOK`, `DEPLOY`, `SECRETS`,
      `docs/DATA-RETENTION.md`) — если менялось поведение, эксплуатация или данные
- [ ] проверено на тестовом окружении: смоук из `DEPLOY.md` §5.1
- [ ] для фронта: `npm run build`, `npm run verify`, при необходимости `npm run verify:admin`
- [ ] нет новых секретов в репозитории и логах; нет `console.log` с персональными данными
- [ ] изменения можно откатить (код — `rollout undo`, данные — восстановление из дампа)
- [ ] выпущено по `DEPLOY.md`, в трекере отмечены версия и ответственный

## 3. Чек-лист ревью PR

### 3.1 Общее

- [ ] описание PR объясняет **зачем**, а не только «что»; есть ссылка на задачу
- [ ] дифф минимален, нет случайных файлов (`.env`, дампы, `dist`, скриншоты с секретами)
- [ ] стиль соответствует окружению (ESM, 4 пробела в backend, 2 в frontend по eslint)
- [ ] `npm run lint` проходит в затронутом пакете

### 3.2 Backend: корректность и данные

- [ ] все запросы к растениям/поливам/фото фильтруются по `user_id` (нет IDOR)
- [ ] админ-маршруты под `requireAdmin`; проверка «нельзя удалить себя/последнего админа»
- [ ] валидация входа: типы, длины, allowlist значений; ошибки `400` с понятным текстом
- [ ] транзакции там, где меняются несколько таблиц; блокировки `LOCK.UPDATE` для
      конкурентных изменений полива/расписания
- [ ] миграция: `IF NOT EXISTS`, без удаления/переименования колонок в одном релизе,
      без блокирующих `ALTER` на больших таблицах без необходимости
- [ ] схема совпадает с моделями (production-старт проверяет схему и падает при расхождении)
- [ ] фоновые задачи под `withDistributedLock`, идемпотентны, не дублируют push/письма
- [ ] лимиты (rate-limit) для новых публичных/админских маршрутов заданы осознанно

### 3.3 Backend: безопасность

- [ ] нет новых секретов в коде, тестах, логах, комментариях, фикстурах
- [ ] cookie/сессия: не ослаблены `httpOnly`/`Secure`/`SameSite`, отзыв сессий работает
- [ ] проверки `Origin`/`Sec-Fetch-Site` не обойдены новым маршрутом
- [ ] SQL только параметризованный (bind/replacements), нет конкатенации ввода
- [ ] файлы: проверка сигнатуры, ограничение размера, allowlist путей, генерация имён
- [ ] ответы не раскрывают существование аккаунта и внутренние ошибки
- [ ] персональные данные не попадают в `admin_audit_logs` (ключи `password|token|cookie|secret`
      вырезаются `utils/adminAudit.js`) и в логи

### 3.4 Frontend

- [ ] нет токенов в `localStorage`/`sessionStorage`, только cookie-сессии с
      `credentials: 'include'`
- [ ] доступность: клавиатурная навигация, фокус, `aria-*`, контраст; не ломается skip-link
- [ ] CSP и security-заголовки не ослаблены (`npm run verify`, `.htaccess` админки)
- [ ] нет внешних скриптов/шрифтов, добавленных без проверки лицензии
      (`THIRD_PARTY_NOTICES.md`)
- [ ] состояния загрузки/ошибки обработаны, нет «пустого экрана» при 401/403/429/503
- [ ] тексты без обещаний и без «ИИ всё знает»; ошибки ИИ объяснены пользователю

### 3.5 Документация и релиз

- [ ] обновлён `docs/api/openapi.yaml` и `CHANGELOG.md`
- [ ] при изменении env-переменных обновлены `Backend/.env.example`, `README.md`,
      `SECRETS.md` и ConfigMap/Secret (`Backend/k8s/10-configmap.yaml`, `deploy.ps1`)
- [ ] при изменении схемы/сроков хранения обновлён `docs/DATA-RETENTION.md`
- [ ] указан план выкладки и отката (для рискованных изменений)

## 4. Обязательные автоматические проверки (CI)

`.github/workflows/ci.yml` на push/PR:

| Job | Что делает |
| --- | --- |
| `frontend` | `npm ci` → `npm run lint` → `npm test` → `npm run build` → `npm run verify` → артефакт `build-info.json` (14 дней) |
| `backend` | `npm run lint` → `npm test` → подготовка БД (`scripts/init-integration-db.mjs`) → применение всех миграций (`ON_ERROR_STOP=1`) → **повторный прогон миграций** (идемпотентность) → `RUN_INTEGRATION=1 npm run test:integration` на сервисах PostgreSQL и Redis |
| `security` | `npm audit --audit-level=high` (backend и frontend), `gitleaks` (скан секретов, полная история), CodeQL (`javascript-typescript`, `security-and-quality`), загрузка SARIF |
| `notify-failure` | создаёт/обновляет issue с меткой `ci-failure` при падении |
| `a11y-smoke` | опционально: axe-smoke (`/`, `/login`, `/home`), E2E, admin-smoke |

Дополнительно в репозитории: `.github/dependabot.yml` (автоматические PR обновлений
зависимостей) и `Backend/scripts/load-test.k6.js` (нагрузочный профиль, требует
установленного k6).

## 5. Календарь регулярных проверок

| Проверка | Периодичность | Ответственный (роль) | Как выполнять | Куда фиксировать |
| --- | --- | --- | --- | --- |
| Пентест / внешний аудит безопасности | **1 раз в 12 месяцев** и перед крупным релизом с новыми данными | владелец продукта (организует) | внешний подрядчик или внутренний чек-лист OWASP ASVS; отдельно — проверка админки и API | отчёт, задачи по находкам |
| Нагрузочный прогон | **1 раз в 6 месяцев** и перед ожидаемым ростом | владелец продукта | `k6 run Backend/scripts/load-test.k6.js` (параметры — в шапке скрипта) на тестовой среде, не на проде | отчёт: RPS, p95/p99, ошибки, узкие места |
| Тест восстановления из бэкапа (restore) | **1 раз в квартал**; после изменения `backup.sh`/CronJob | владелец продукта | `RUNBOOK.md` §7 на отдельной БД: восстановить дамп, применить миграции, проверить `/health` и смоук; замерить фактическое время (RTO) | запись: дата, дамп, время восстановления, расхождения |
| Проверка свежести бэкапов | **ежемесячно** (и после релизов) | владелец продукта | наличие `Backend/backups/.last-success` (compose) / `/backups/.last-success` (k8s), размер, `pg_restore --list` | отметка в трекере |
| Ревизия доступов | **1 раз в квартал** | владелец продукта | список лиц с доступом к серверу, кластеру, БД, FTP, почте, Yandex Cloud, GitHub, админке; удалить лишнее | реестр доступов (вне репозитория) |
| Ротация секретов | **по `SECRETS.md`**: SECRET_KEY/DB/Redis/AI/VAPID — 12 мес.; SMTP/FTP — 6–12 мес.; TLS — автоматически | владелец продукта | `RUNBOOK.md` §8, запись в журнале `SECRETS.md` §4 | журнал ротаций |
| Проверка TLS | **ежемесячно** + алерт за 30 дней до истечения | владелец продукта | `docker compose -f Backend/docker-compose.yml exec certbot certbot certificates`; проверить сайт, API, админку | отметка + срок |
| Ревизия лицензий и зависимостей | **1 раз в 6 месяцев** и при смене крупных версий | владелец продукта | `npm audit`, обновления через dependabot, сверка `THIRD_PARTY_NOTICES.md` (в т.ч. MPL-2.0/LGPL/OFL) | обновлённый `THIRD_PARTY_NOTICES.md` |
| Проверка действия GDPR/152-ФЗ процедур | **1 раз в год** | владелец продукта + юрист | запрос «экспорт данных» и «удаление аккаунта» на тестовом аккаунте; проверка текстов уведомлений | запись в трекере |
| Ревизия сроков хранения | **1 раз в год** и при изменении переменных retention | владелец продукта | сверка `docs/DATA-RETENTION.md` с `jobs/cleanExpiredTokens.js` и фактическими логами очистки | обновлённый документ |
| Просмотр `admin_audit_logs` | **ежемесячно** | владелец продукта | `GET /api/admin/audit` (админка) — массовые удаления, смена ролей, подозрительная активность | отметка + разбор при аномалиях |
| Проверка мониторинга и алертов | **1 раз в квартал** | владелец продукта | `/health`, `/livez`, `/api/system/metrics`, heartbeat бэкапа; проверить, что падение действительно заметят | отметка |
| Обновление документации по итогам инцидентов | после каждого SEV-1/SEV-2 | лид инцидента | `INCIDENT-RUNBOOK.md` §8 | правки в этом репозитории |
