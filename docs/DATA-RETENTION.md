# DATA-RETENTION.md — сроки хранения, удаление и экспорт данных

Документ закрывает аудит-пункты L1.3 (сроки хранения, удаление, экспорт, ответы на запросы
субъекта) и L1.9 (публикация изменений документов и уведомление пользователей), а также
фиксирует, что остаётся в резервных копиях.

Источник истины — код: `Backend/jobs/cleanExpiredTokens.js`, `Backend/controllers/accountController.js`,
`Backend/controllers/userController.js`, `Backend/migrations/*.sql`, `Backend/backup.sh`,
`Backend/k8s/jobs/db-backup.cronjob.yaml`. Ответственный за соблюдение сроков и ответы на
запросы субъектов — **владелец продукта** (роль).

## 1. Что и сколько хранится

Ежедневная очистка (`startCleanupJob`, лок `job:cleanup-expired`, раз в 24 часа и при
старте backend) удаляет данные по срокам ниже. Значения `0` для переменных срока означают
«хранить бессрочно» (кроме случаев, где срок задан константой в коде).

| Данные | Таблица / файлы | Срок хранения | Чем управляется |
| --- | --- | --- | --- |
| Сообщения чата пользователей | `chat_logs` (`user_id IS NOT NULL`) | **365 дней** | `CHAT_LOG_RETENTION_DAYS` (по умолчанию 365) |
| Сообщения чата гостей | `chat_logs` (`user_id IS NULL`) | **180 дней** | константа `GUEST_DATA_RETENTION_MS` в `cleanExpiredTokens.js` |
| Журнал подсказок ИИ | `ai_advice_logs` | **365 дней** (при удалении аккаунта `user_id` обнуляется, запись остаётся обезличенной) | `AI_ADVICE_LOG_RETENTION_DAYS` |
| In-app уведомления | `notifications` | **180 дней** | `NOTIFICATION_RETENTION_DAYS` |
| Гостевые cookie-согласия | `user_cookie_consents` (`user_id IS NULL`) | до 180 дней с создания; истекающие — через 30 дней после `expires_at` | константы в `cleanExpiredTokens.js` |
| Согласия пользователя | `user_cookie_consents`, `user_legal_consents` (`user_id` задан) | пока существует аккаунт (без автоматического удаления) | — |
| Сессии и токены | `auth_sessions` | истёкшие удаляются сразу, отозванные — через 30 дней | `cleanExpiredTokens.js` |
| Челленджи passkey | `passkey_challenges` | до истечения (`expires_at`) | `cleanExpiredTokens.js` |
| Токены сброса пароля | `password_reset_tokens` | истёкшие/использованные — через 30 дней | `cleanExpiredTokens.js` |
| Push-подписки гостей | `push_subscriptions` (`user_id IS NULL`) | **30 дней** без обновления | `GUEST_PUSH_RETENTION_DAYS` |
| Недействительные push-подписки | `push_subscriptions.invalidated_at` | **30 дней** после инвалидации | `INVALIDATED_PUSH_RETENTION_DAYS` |
| Статистика посещений | `site_visit_days` | **400 дней** | константа `VISIT_RETENTION_DAYS` |
| Журнал действий администратора | `admin_audit_logs` | **365 дней** (append-only) | функция `purge_admin_audit_logs()` (вызывается ежедневной очисткой) |
| Фото растений | `plant_photos` + `Backend/uploads/plants` | пока существует растение; осиротевшие файлы удаляются ежедневно | `cleanOrphanedPlantPhotoFiles` |
| Миниатюры фото | `Backend/uploads/thumbs` | пересоздаются; удаляются вместе с осиротевшими файлами | `plantPhotoCleanup.js` |
| Фото в чате | `Backend/uploads/chat` + `chat_logs.metadata.photoUrl` | ссылки живут вместе с сообщением; **файлы при ретенционной очистке `chat_logs` не удаляются** (известный пробел) | удаление — при удалении аккаунта (`removeChatPhotoFiles`) |
| Резервные копии (compose) | `Backend/backups/*.dump`, `uploads_*.tar.gz` | **14 дней** | `BACKUP_RETENTION_DAYS` (по умолчанию 14), `backup.sh` |
| Резервные копии (Kubernetes) | PVC `backend-backups`, `db-<stamp>.dump` | **14 дней** | `jobs/db-backup.cronjob.yaml` (`BACKUP_RETENTION_DAYS=14`) |
| Логи приложения | stdout контейнера / `kubectl logs` | по настройкам Docker/кластера | не регламентировано в приложении |

Дополнительно:

* push-подписка привязывается к аккаунту при входе; при удалении аккаунта удаляются и
  подписки;
* при удалении записи чата/сессии из админки файлы фото чата также не удаляются (пробел
  тот же);
* `site_visit_days` не содержит IP-адресов: хранятся случайный `visitor_id`, путь входа,
  хост перехода, тип устройства и счётчик просмотров.

## 2. Как удаляются данные

### 2.1 Автоматическая очистка

Запускается при старте backend и далее раз в 24 часа (`BACKUP`-независимо), под
распределённым локом Redis:

```powershell
# состав очистки виден в логах backend
docker compose -f Backend/docker-compose.yml logs backend | Select-String "Очищено|Уведомления:"
```

Что делает `cleanExpiredAuthData()`:

1. гостевые cookie-согласия (по `expires_at` и возрасту);
2. гостевые сообщения чата старше 180 дней;
3. сообщения пользователей старше `CHAT_LOG_RETENTION_DAYS`;
4. журнал подсказок ИИ старше `AI_ADVICE_LOG_RETENTION_DAYS`;
5. истёкшие `auth_sessions`, `passkey_challenges`, `password_reset_tokens`;
6. осиротевшие файлы фото растений (нет строки в `plant_photos`);
7. `site_visit_days` старше 400 дней;
8. уведомления старше `NOTIFICATION_RETENTION_DAYS`;
9. гостевые и инвалидированные push-подписки;
10. `admin_audit_logs` старше 365 дней — только через `purge_admin_audit_logs()`
    (таблица append-only, прямой `DELETE`/`UPDATE` запрещён триггером).

### 2.2 Удаление аккаунта пользователем

`DELETE /api/users/me` (требует `confirm: "УДАЛИТЬ"` и пароль; аккаунт `ADMIN` так удалить
нельзя). В одной транзакции удаляются:

* растения, их фото (строки + файлы на диске), поливы, планы ухода;
* сообщения чата, уведомления, настройки уведомлений, push-подписки;
* cookie- и юридические согласия, сессии, passkeys, челленджи, токены сброса пароля;
* строки получателей push/email-рассылок.

Обезличиваются (запись остаётся, персональная связь теряется):

* `ai_advice_logs.user_id` → `NULL`;
* `site_visit_days.user_id` → `NULL`;
* `push_broadcasts.created_by` / `mail_broadcasts.created_by` → `NULL`.

Ответ: `{"deleted": true, "removed": {…счётчики…}}`. Файлы фото удаляются после коммита
транзакции; неудалённые файлы добирает суточная очистка.

### 2.3 Удаление администратором

`DELETE /api/admin/users/{id}` делает то же самое; запрещено удалять собственную учётную
запись и последнего администратора (`400`/`409`). Действие фиксируется в
`admin_audit_logs`.

## 3. Экспорт данных (право субъекта на доступ)

| Способ | Что отдаёт | Ограничения |
| --- | --- | --- |
| `GET /api/users/me/export` | JSON-файл `lejka-account-<id>-<YYYY-MM-DD>.json`, `format: webplant-account-export`, `formatVersion: 1`: профиль, растения с планами ухода и фото, поливы, сообщения чата, журнал ИИ, уведомления, настройки, push-подписки (без ключей), согласия, passkeys (без ключей), счётчик сессий, посещения | 10 запросов в час; `Cache-Control: no-store`; push-подписки и passkeys отдаются без секретов |
| `GET /api/plants/export` | CSV активных растений (BOM UTF-8, `;`, даты в часовом поясе пользователя) | до 5000 растений; только активные растения |

**Известное ограничение экспорта:** в `wateringLogs` JSON-экспорта поля `wateredAt`,
`daysLate`, `comment` формируются из несуществующих атрибутов модели
(`action_at`, `hours_late`, `note`), поэтому в выгрузке они приходят пустыми. До исправления
для полной истории поливов используйте `GET /api/plants/history` или CSV
`GET /api/plants/export`. Пробел зафиксирован в `CHANGELOG.md` (Unreleased).

### 3.1 Порядок ответа на запрос субъекта

1. Запрос приходит на адрес поддержки/владельца продукта; регистрируется в трекере
   (дата, субъект, требование).
2. Личность подтверждается: запрос с авторизованной сессии либо ответ на письмо с адреса,
   совпадающего с email аккаунта.
3. Владелец продукта выгружает данные (`GET /api/users/me/export` из сессии
   пользователя или административная выгрузка) и передаёт файл субъекту защищённым
   каналом.
4. Удаление — по процедуре §2.2 (самостоятельно) или §2.3 (администратором).
5. Ответ направляется в срок, установленный законом (ориентир по 152-ФЗ — 10 рабочих дней
   с возможным продлением; точный срок и форму ответа подтверждает юрист).
6. Факт запроса и ответа фиксируется в журнале обращений (без копирования самих
   персональных данных).

## 4. Что остаётся в резервных копиях

* Бэкапы делаются **ежедневно** и хранятся **14 дней**; удалённые по запросу данные
  остаются в дампах до истечения этого срока (RPO — 24 часа, см. `RUNBOOK.md` §9).
* В compose-стеке `backup.sh` сохраняет дамп БД **и** архив `uploads`; в Kubernetes CronJob
  `db-backup` сохраняет **только дамп БД** (фото восстанавливаются из архива,
  подготовленного отдельно, см. `DEPLOY.md` §1.2 и `RUNBOOK.md` §7.3).
* Опционально: шифрование (`BACKUP_ENCRYPTION_PASSPHRASE`, gpg или age) и выгрузка offsite
  (`BACKUP_OFFSITE_TARGET`, rclone). Если включено, пароль/цель хранятся в секретах
  (`SECRETS.md`), а факт шифрования фиксируется в heartbeat-файле `.last-success`.
* Если субъект требует немедленного удаления «отовсюду», это означает также удаление
  соответствующих файлов бэкапа вручную — операция необратима и выполняется владельцем
  продукта с фиксацией в журнале; по умолчанию данные исчезают из бэкапов в течение
  14 дней естественным образом.
* Отдельного «холодного» архива с длительным хранением нет.

## 5. Публикация изменений документов и уведомление пользователей (L1.9)

Документы: Политика конфиденциальности, Согласие на обработку персональных данных,
Пользовательское соглашение (файлы в `Frontend/document/`: PDF/DOCX; публикация — на
сайте). Версии фиксируются в БД:

* `user_legal_consents.document_version` — текущая версия, с которой принимаются согласия
  при регистрации (`'2.0'` в `Backend/controllers/userController.js`);
* `user_cookie_consents.version` — версия cookie-политики;
* каждое принятие/отзыв хранит `accepted_at`, `revoked_at`, `source`
  (`registration`, `settings`, `banner`, `legal_update`), IP и user-agent.

### 5.1 Порядок публикации

1. **Черновик.** Владелец продукта готовит новую редакцию и краткое описание изменений
   (что меняется и почему, какие данные и сроки затрагиваются).
2. **Проверка.** Юридическая проверка (внешний юрист или штатный), проверка фактов
   ответственным за инфраструктуру: сроки хранения, перечень данных, получатели
   (Yandex Cloud, почтовый провайдер, push-сервисы), способы удаления/экспорта.
3. **Версионирование.** Номер версии увеличивается; файлы в `Frontend/document/`
   обновляются одновременно с текстом на сайте; в репозитории фиксируется коммит с
   описанием изменений.
4. **Публикация.** Новая редакция выкладывается на сайт (frontend-деплой, см. `DEPLOY.md`
   §4) и доступна по постоянной ссылке; старая редакция сохраняется в архиве сайта или
   репозитория (для доказуемости).
5. **Уведомление пользователей.** Если изменения затрагивают права/обязанности:
   * баннер на сайте при следующем входе (со ссылкой на новую редакцию и датой
     вступления в силу);
   * при существенных изменениях — письмо по SMTP (только пользователям с
     `marketing_email_opt_in = true`; сервисные письма, например о смене условий
     аккаунта, отправляются независимо от маркетингового согласия и требуют юридической
     проверки);
   * запись в `CHANGELOG.md` (раздел Unreleased/релиз) и, при необходимости, в
     статус-канале.
6. **Фиксация согласий.** При следующем принятии документов пишутся строки с
   `source = 'legal_update'` и новой `document_version`; отзыв — через
   `PUT /api/cookie-consents/{consentType}/revoke`.
7. **Срок вступления в силу.** Устанавливает владелец продукта по согласованию с юристом
   (ориентир — не менее 10 календарных дней после публикации для существенных изменений);
   дата публикуется вместе с новой редакцией.

### 5.2 Минимальный чек-лист публикации

- [ ] новая редакция проверена юристом, замечания закрыты
- [ ] версия документа увеличена, файлы и страница на сайте обновлены одновременно
- [ ] перечень данных, сроки хранения и получатели совпадают с этим документом и кодом
- [ ] опубликована дата вступления в силу
- [ ] уведомление отправлено (баннер/письмо), текст согласован
- [ ] в `CHANGELOG.md` есть запись об изменении документов
- [ ] факт публикации и уведомления зафиксирован в журнале (дата, кто, канал)

## 6. Маркетинговые рассылки и отписка

* Отдельное согласие на маркетинговые письма хранится в `users.marketing_email_opt_in`
  (+ `marketing_email_opt_in_at`, `_source`, `marketing_email_opt_out_at`); по умолчанию
  `false`, в том числе для существующих аккаунтов.
* Аудитория рассылки — только `marketing_email_opt_in = true`; отчёт о рассылке в админке
  показывает, сколько получателей без согласия или отписались.
* Отписка в один клик (RFC 8058): `GET/POST /api/users/unsubscribe?uid=<id>&token=<token>`
  отдаёт HTML-страницу подтверждения; токен — HMAC-SHA256 от `unsubscribe:<user_id>` на
  `SECRET_KEY`, в БД не хранится, бессрочен до смены `SECRET_KEY` (после ротации старые
  ссылки перестают работать — см. `RUNBOOK.md` §8.1).
* Повторная отписка идемпотентна и не переписывает дату `marketing_email_opt_out_at`.

## 7. Сводка для политики конфиденциальности

| Категория | Срок |
| --- | --- |
| Аккаунт и профиль | до удаления аккаунта |
| Растения, поливы, фото | до удаления растения/аккаунта; осиротевшие файлы — ежедневно |
| Переписка с ИИ-помощником | 365 дней (пользователь), 180 дней (гость) |
| Журнал подсказок ИИ | 365 дней (обезличивается при удалении аккаунта) |
| Уведомления | 180 дней |
| Согласия | до удаления аккаунта (гостевые — 180 дней) |
| Сессии, токены, челленджи | до истечения и не более 30 дней после отзыва/истечения |
| Статистика посещений | 400 дней, без IP |
| Журнал действий администратора | 365 дней |
| Резервные копии | 14 дней |

Изменения этого документа публикуются по процедуре §5; при изменении сроков требуется
синхронное обновление политики конфиденциальности и уведомление пользователей.
