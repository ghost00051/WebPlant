# Аудит механизмов полива WebPlant / «Лейка»

**Роль:** tech lead / senior review
**Дата:** 2026-10-19
**Предмет:** назначение полива (интервалы/время/расписание), отметки (полив/пропуск/удаление/бэкфилл), напоминания (push + in-app), производные данные (история, статистика, календарь).
**Метод:** статический разбор всего контура полива + 3 воспроизводимых Node-пробы против реальных утилит (`Backend/utils/wateringSchedule.js`) + прогон бэкенд-тестов. Живой БД/сервера на машине не было — динамические сценарии с настоящим Postgres/Redis/web-push не выполнялись (см. §7).

## 0. Вердикт

Контур полива сделан грамотнее, чем типичный «cron + поле next_watering_at»:

* часовые пояса действительно персональные (IANA из браузера → `users.timezone`), и почти весь расчёт идёт через zoned-арифметику, а не через «сырые» миллисекунды;
* авторизация/изоляция данных в порядке — ни одной IDOR-дыры в контуре растений/поливов/логов я не нашёл;
* валидация входных данных на API плотная (интервал 1–365, enum времени, дни недели 0–6 без дублей, лимиты строк, фото только из `/uploads/plants/<hash>`);
* ИИ-рекомендация частоты/времени полива изолирована валидацией, бюджетом, дедлайном, кэшем и детерминированным фолбэком;
* запись полива/пропуска/удаления идёт в транзакциях с `SELECT ... FOR UPDATE`, есть аудит `converted_from_skip`.

Но есть **три системные проблемы**, которые я бы не выпускал в прод без решения:

1. **Авто-пропуск (`autoSkipOverdue`) молча убирает неполитое растение из «Сегодня нужно полить» и сдвигает график на интервал вперёд.** Приложение при этом может показать «Все растения политы 💚». Пользователь не получает ни уведомления о пропуске, ни шанса полить растение, пока сам не откроет календарь. Для заброшенных аккаунтов это превращается в вечный генератор `skipped`-строк и push-спам.
2. **«Следующий полив» вычисляется в четырёх разных местах четырьмя разными способами** (`water`, `skip`, `update`, `autoSkipOverdue`) — и формулы расходятся (DST, короткие интервалы, никогда не политые растения). Это источник «плавающих» дат, которые потом невозможно объяснить пользователю.
3. **Напоминания доделаны наполовину:** push-ветка не изолирована по растению/получателю (одна ошибка рвёт весь тик), у `web-push` нет таймаута, in-app уведомления вообще не отображаются и никогда не помечаются прочитанными, а специальные тесты на расписание были удалены.

Оценка по срезам (субъективно, 10-балльная):

| Срез | Оценка | Комментарий |
|---|---|---|
| Адекватность алгоритма | 6/10 | таймзоны и база верные, но авто-пропуск, бэкфилл и пересчёты дают «фантомные» состояния |
| Отказоустойчивость | 5/10 | тик не изолирован, push без таймаута/ретраев, нет retention, PWA показывает устаревшие данные |
| Безопасность | 8/10 | IDOR/CSRF/инъекций нет; минусы — отсутствие лимитов на write-эндпоинты полива и полуоткрытый `scheduled_for` |
| Согласованность данных | 5/10 | `last_watered_at` может ссылаться на удалённую запись, `on_time` завышается, статистика в UTC-днях |
| UX/прозрачность | 5/10 | необъяснимые сдвиги дат, ночные push, счётчик уведомлений без экрана |

Release-блокеров уровня «не деплоить» я в этом контуре не нашёл, но P1-пункты ниже я бы закрыл до следующего релиза.

## 2. Как устроен полив сейчас (карта, для контекста)

* **Данные:** `plants.next_watering_at` (timestamptz) — единственный источник «когда полить»; `watering_interval_days` 1–365; `watering_time_of_day` ∈ `{morning:9, day:14, evening:19}`; `last_watered_at`; `reminder_weekdays` (JSONB, 0=Вс); `metadata.notifications` — ad-hoc флаги, чтобы не дублировать push.
* **События:** `watering_logs(action watered|skipped, action_at, scheduled_for, hours_late, note, metadata.prev_next_watering_at)`. `metadata.prev_next_watering_at` нужен, чтобы откатить расписание при удалении отметки.
* **Расчёт:** `nextWateringInstant(from, days, timeOfDay, timeZone)` — прибавить дни к локальной дате и выставить локальный час (zoned-арифметика через `Intl`).
* **Отметка «полить сейчас»:** `POST /plants/:id/water` без тела — `last_watered_at=now`, `next=now+interval`, лог с `scheduled_for = прежний next`, `hours_late=round(now-scheduled)`.
* **Отметка «полить за прошлый слот» (из календаря):** `POST /water {scheduled_for}` — `resolvePastWatering`: `action_at = слот`, `hours_late = 0`, `next = max(текущий next, слот+interval)`, может конвертировать `skipped` → `watered`.
* **Пропуск:** `POST /skip` — сдвигает `next` на N дней от текущего next, пишет `skipped`; UI его не использует (эндпоинт живой).
* **Напоминания:** `node-cron` каждые 10 минут UTC, распределённый лок в Redis. Внутри: авто-пропуск → утренняя сводка (локальные 09:00 у каждого пользователя) → «за день» (окно `now+20h…now+28h`) → «в день» (`next ∈ [now−5min, now+15min]`). Плюс запись в `notifications` (уникальный `(user_id, dedupe_key)`).
* **Отображение:** `/need-watering` (`next < локальная полночь завтра`), `/schedule` (90 дней вперёд по occurrences), `/timeline` (500 последних логов + текущие просрочки), `/stats/completion`.

## 3. Находки

Приоритеты: **P1** — исправлять до релиза, **P2** — в ближайший спринт, **P3** — техдолг/гигиена, **P4** — мелочи. Пометка «как в отчёте» — уже фиксировалось в `Release-Verification-Report.md`; здесь указан текущий статус.

### P1-1. Авто-пропуск прячет неполитое растение и молча сдвигает график
`Backend/jobs/reminderService.js:98-173`, `:175-187`; `Backend/controllers/plantController.js:1348-1369`; `Frontend/src/component/homePage/homePage.jsx:595-609`.

Сценарий (проверено по коду): растение должно поливаться в Пн 09:00, пользователь не полил. Во вторник 09:10 тик видит `next < now−24h` и:
1. пишет `skipped` с `scheduled_for=Пн 09:00`, `hours_late=24`;
2. двигает `next` на следующий интервал (для 7 дней — на Пн следующей недели);
3. обнуляет `metadata.notifications`.

Дальше `GET /need-watering` (`next < завтрашняя полночь`) его уже не возвращает → главный экран показывает «Все растения политы 💚», хотя растение не полито и физически может пересохнуть. Push о пропуске не отправляется. Пользователь узнает о случившемся только если откроет календарь и увидит событие «Пропущено».

Для неактивных аккаунтов это самоподдерживающийся цикл: каждые 1–7 дней появляется новая `skipped`-строка, шлётся «Пора полить!», человек игнорирует, цикл повторяется — безлимитно (retention нет, см. P2-9).

**Рекомендация.** Не менять `next` молча, пока пользователь не взаимодействовал: держать растение в состоянии «просрочено» и в `need-watering`, а факт пропуска показывать отдельным бейджем. Если авто-пропуск остаётся продуктовым решением — минимум: (а) push/уведомление «полив пропущен, растение всё ещё ждёт воды» с deep-link на этот слот; (б) не убирать его из «Сегодня нужно полить», а помечать «пропущено, полить сейчас»; (в) после N подряд пропусков — пауза напоминаний/архивация растения, чтобы не спамить.

### P1-2. Короткие интервалы: авто-пропуск «съедает» лишний слот и теряет записи
`Backend/jobs/reminderService.js:132-148`.

```js
const periodsToAdvance = Math.floor((now - scheduledFor) / intervalMs) + 1
const nextWatering = new Date(scheduledFor.getTime() + periodsToAdvance * intervalMs)
```

Грейс-порог — `now > scheduledAt + 24h`, а следующий слот ищется как «первый строго после `now`». Для `intervalDays = 1` эти два условия сталкиваются: каждый следующий слот наступает ровно тогда, когда истекает грейс предыдущего.

Проверка: `scheduled=Пн 09:00`, `interval=1`, тик `Вт 09:10` → `periods=2` → `next=Ср 09:00`. Слот Вт 09:00 был просрочен всего на 10 минут, но уже «пропущен» — и в лог он не попал. Итог для «Каждый день»: растение после первого пропуска становится «через день», а не ежедневным.

Тот же механизм при длительном отсутствии (30 дней, interval=1) продвигает `next` на 31 период, но пишет **один** `skipped`-лог. `skipped_count`, история и completion-статистика теряют 30 событий (в дампе `pre_auth_migration.sql:861-873` видно ровно такие ежедневные авто-пропуски).

**Рекомендация.** Считать следующий слот как «первый, у которого ещё не истёк собственный 24-часовой грейс»: `next = первое occurrence, для которого occurrence + grace > now`; пропуски логировать по каждому occurrence (или писать `metadata.missed_count`). Плюс явно задокументировать семантику грейса.

### P1-3. Один и тот же «Полить» из разных мест пишет разные данные (0 часов опоздания)
`Backend/controllers/plantController.js:969-1141`; `Backend/utils/wateringSchedule.js:241-273`; `Frontend/src/component/visionNextPlant/visionNextPlant.jsx:261-275, 375-390`; `Frontend/src/component/homePage/homePage.jsx:329-365`.

* Кнопка «Полить» в списке «Сегодня нужно полить» → `water()` без тела → `action_at=now`, `hours_late >= 0` (реально посчитанное опоздание).
* Кнопка «Полить» на просроченной/пропущенной дате в календаре → `water({scheduled_for})` → `resolvePastWatering` → `action_at = слот`, `hours_late = 0`, `last_watered_at = max(prev, слот)`.

То есть **одно и то же действие пользователя фиксируется по-разному в зависимости от точки входа**: из календаря система считает, что полив был выполнен вовремя в день слота. Это не случайность — удалённые тесты (`45225b0^:Backend/utils/wateringSchedule.test.js`: *«past watering closes the overdue slot… hoursLate 0»*, *«the day of a converted missed watering stops being overdue»*) фиксировали именно такое намерение. Но пользователь видит одну и ту же кнопку «Полить» и, скорее всего, ожидает «я полил сейчас», а не «я подтверждаю, что полил тогда».

Следствия: `on_time_rate` и `avg_hours_late` в `getStats` не отражают реальность для календарных отметок; на таймлайне просроченное событие превращается в аккуратный «полито» без опоздания; при конверсии авто-пропуска исходный auto-skip сохраняется только в `metadata.converted_from_skip`.

**Рекомендация.** Развести два намерения явно: «Полить сейчас» (по умолчанию; `action_at=now`, `scheduled_for=слот`, `hours_late=now−слот`) и «Отметить задним числом» (отдельное действие/чекбокс; `action_at=слот`). Если продуктовое решение — оставить бэкфилл, переименовать кнопку/добавить подтверждение и не считать это «вовремя» в статистике.

### P2-1. Один сбойный пуш/растение обрывает весь тик напоминаний
`Backend/jobs/reminderService.js:260-322`, `:348-373`, `:175-187`; `Backend/services/pushService.js:59-116`.

В `sendDayBefore` и `sendOnDay` цикл по растениям **без `try/catch`**. `notify()` дергает `storeNotification` (может кинуть unique violation при гоночном `findOrCreate`) и `pushService.sendToUser` (может кинуть `ensureConfigured`, ошибку БД). Любое исключение выходит из `sendDayBefore` в `tick`, где стоит один общий `try` — и `sendOnDay` в этом тике уже не выполняется. Если «ядовитое» растение повторяется в выборке, часть пользователей не получит напоминания на каждом тике.

Важно: в `Release-Verification-Report` п. N8/P2-11 заявлено «per-plant try/catch, цикл продолжается». Фактически это добавлено **только** в `autoSkipOverdue` (`:108-172`); в двух отправителях напоминаний изоляции нет. То есть пункт закрыт частично — стоит переоткрыть.

Дополнительно: `webpush.sendNotification` вызывается без опции `timeout` (`pushService.js:75-89`). В `web-push@3.6.7` таймаут поддерживается (`node_modules/web-push/src/web-push-lib.js:222-223, 317-318`), но не передан: зависший endpoint Apple/FCM держит тик, следующий тик отсекается локом, напоминания другим пользователям теряются.

**Рекомендация.** `try/catch` на каждое растение; `Promise.allSettled` + ограниченная конкурентность (5–10) на подписки; `timeout: 10_000` в `sendNotification`; отдельный `try` на каждую из четырёх стадий тика; метрика `push_failed`.

### P2-2. Потеря push при нуле подписок / переотправки без ретрая *(как в отчёте 6.4, OPEN)*
`Backend/services/pushService.js:28-34`; `Backend/jobs/reminderService.js:286-288, 318-320, 249-251`.

При отсутствии подписок `sendToUser` возвращает `{success:false, message:'No subscriptions'}` — **без `sent`**, поэтому `result.sent > 0` = `undefined > 0` = false. `last_morning_summary_date`/`metadata.notifications` в этом случае не обновляются: утренняя сводка пересчитывается на каждом тике в течение часа, `storeNotification` вызывается повторно (dedupe-строка не плодится, но работа/логи идут), а in-app запись уже лежит — увидеть её негде (см. P2-6).

Ретрая «недоставленного» push нет вообще: если `sendToUser` упал (сеть/VAPID/временный 500), слот выходит из окна через 10–20 минут, и уведомление потеряно навсегда.

**Рекомендация.** Всегда возвращать числовые `{total, sent, failed, removed}` (`sent:0` в early-return); хранить в `notifications` признак `push_sent_at/push_attempts`; bounded-retry (2–3 попытки в течение окна); разделить «слот закрыт» и «push доставлен».

### P2-3. DST-дрейф: авто-пропуск и календарь используют миллисекунды вместо zoned-арифметики
`Backend/jobs/reminderService.js:136-140`; `Backend/utils/wateringSchedule.js:153-168` (`generateWateringOccurrences`, интервал в мс); `Frontend/src/component/visionNextPlant/visionNextPlant.jsx:31-42` (жёстко зашитые «9:00/14:00/19:00»).

Для поясов с переходом на летнее время (пользователь может быть в любом IANA-поясе, `isValidTimeZone` это разрешает):

```
next = 2026-03-25 08:00Z (09:00 Берлин, CET), interval=7
getSchedule → 2026-04-01 08:00Z = 10:00 Берлин (CEST), далее всегда 10:00
autoSkip → тот же сдвиг: next = 10:00, а не 09:00
```

Пользователь выбрал «Утро, 9:00», UI подписывает слоты «9:00», но напоминание придёт в 10:00, а календарь содержит 10:00. Москва/DST-зоны РФ не задеты, но часовой пояс у нас персональный и произвольный.

**Рекомендация.** Генерировать occurrences итеративно через `zonedDayHourAfter(previous, interval, hour, tz)` (функция уже есть), а не `+ intervalDays*86400000`; в авто-пропуске — то же. В UI вместо констант брать `watering_time_of_day` → час (а ещё лучше — отдавать с сервера `local_time` строкой).

### P2-4. Дедупликация отметок идёт по UTC-суткам, а весь остальной продукт — по локальным
`Backend/utils/wateringSchedule.js:281-325`; `Backend/controllers/plantController.js:1025-1045`.

`utcDayRange(slot)` — это календарные сутки UTC. Но слоты полива 09:00/14:00/19:00 **локального** времени, а `zonedDayKey`/`diffLocalDays`/таймлайн/`need-watering` считают в поясе пользователя. Для пояса UTC+10 слот «19 октября 09:00» = `2026-10-18T23:00Z`, а полив в тот же локальный день в 20:00 = `2026-10-19T10:00Z` — это уже другие UTC-сутки. Проверка «уже отмечено» такую запись не найдёт → повторная отметка/конвертация не того `skipped`. Для Москвы ломается только у полуночи (слот 09:00 MSK = 06:00Z — совпадает, но ручная отметка в 00:30 MSK = 21:30Z предыдущих UTC-суток).

Удалённый тест прямо закреплял UTC-семантику (`wateringSchedule.test.js`: *«watering slot day range covers exactly the UTC day»*) — то есть это осознанное решение, принятое до переезда на персональные таймзоны и не пересмотренное.

**Рекомендация.** Считать границы суток в поясе пользователя (`zonedDayHourAfter(slot, 0, 0, tz)` … `+1 день`), либо искать по окну `scheduled_for ∈ [slot−12h, slot+12h]`; добавить тесты для UTC+10/UTC−8.

### P2-5. Правка карточки растения всегда пересчитывает расписание и сбрасывает флаги уведомлений
`Backend/controllers/plantController.js:722-748`; `Frontend/src/component/myPlant/myPlant.jsx:134-147`.

`scheduleChanged` проверяет **наличие** полей, а не их изменение; редактор `myPlant` всегда отправляет `watering_interval_days` и `watering_time_of_day`, даже если менялось только название. Тогда:

```js
updates.next_watering_at = computeNextWatering(
  updates.last_watered_at ?? plant.last_watered_at ?? new Date(), …)
updates.metadata.notifications = {}
```

Последствия:
* **Никогда не политое растение** (`last_watered_at = null`, а такие есть — создал и не отметил): `next` считается от `now`, а не от прежней фазы. Проверка: создано 01.10, интервал 7, авто-пропуски довели план до 29.10; правка названия 24.10 → `next = 31.10` (+2 дня «на ровном месте»).
* Для политого растения формула фазу сохраняет, но **флаги `metadata.notifications` всё равно сбрасываются**, и если правка случилась внутри окна «за день» (05:00–13:00 локального), `notify()` отправит push повторно — `findOrCreate` вернёт существующую запись, но push уйдёт ещё раз (в `notify` результат `created` не анализируется).
* `update()` не берёт транзакцию/`FOR UPDATE`, в отличие от `water/skip/delete/autoSkip` → гонка с тиком может перетереть только что рассчитанный `next_watering_at` (lost update). То же у `updateMetadata` (`:1479-1502`).

**Рекомендация.** Пересчитывать только при фактическом изменении интервала/времени; для «никогда не политого» — считать от даты создания/текущего `next`, а не от `now` (или применять ту же нормализацию фазы, что autoSkip); сбрасывать `notifications` только если `next` реально изменился; обернуть в транзакцию с блокировкой строки.

### P2-6. `reminder_weekdays` не пересчитывается при сдвиге даты → напоминания молча пропадают
`Backend/jobs/reminderService.js:324-329`; `Backend/controllers/plantController.js:1246-1314`, `:722-748`; `Frontend/src/component/myPlant/myPlant.jsx:396-412`.

Фильтр: ограничение по дням применяется только для интервалов 1 и кратных 7; сравнивается день недели **даты полива** с сохранённым массивом. Но `next` может переехать на другой день недели:

* `POST /skip {days:1}` при интервале 7: Пн → Вт, в БД остаётся `[1]` → на Вт фильтр false → push нет; следующий авто-пропуск сдвинет ещё на +7 (Вс→Вт), т.е. день недели закрепляется неверный — напоминания не приходят уже никогда;
* `update()` с изменением интервала/времени пересчитывает `next` от `last_watered_at`, а `reminder_weekdays` не трогает;
* в `myPlant` кнопки дней недели **всегда активны**, в отличие от `addPlants` (`disabled={!canRestrictWeekdays}`), т.е. интерфейс предлагает выбрать ограничение, которое бэкенд проигнорирует (для интервала 3/4/10 и т.п.).

**Рекомендация.** При любом изменении `next`, `watering_interval_days`, `skip` — пересчитывать `reminder_weekdays` (для кратных 7 — день недели нового `next`, для 1 — оставить выбранные, для остальных — `[]`); в редакторе заблокировать/скрыть выбор дней, как в `addPlants`; либо трактовать фильтр как «день отправки», а не «день полива».

### P2-7. «За день» может прийти в 05:00 локального времени, «в день» — за 15 минут до слота
`Backend/jobs/reminderService.js:260-268`, `:292-302`.

Окно `now+20h … now+28h` в абсолютном времени: для полива завтра в 09:00 первый возможный тик — сегодня в **05:00** локального. Quiet hours нет, отдельного пользовательского времени отправки нет. «В день» срабатывает, когда `next ∈ [now−5min, now+15min]`, т.е. push может уйти на 15 минут раньше слота — для уведомления терпимо, но лучше выравнивать.

**Рекомендация.** Привязать отправку к локальному утру (например, «за день» в 09:00–12:00 локального, «в день» в сам слот ±5 минут), либо добавить настройку quiet hours; для «за день» — окно `[due−20h, due−14h]` с проверкой локального часа.

### P2-8. In-app уведомления пишутся, но нигде не показываются и не помечаются прочитанными
`Frontend/src/component/homePage/homePage.jsx:129-148`, `:550-552`; `Backend/controllers/notificationController.js`; `Backend/routes/notificationRoutes.js`.

### P2-9. `deleteWatering` оставляет `last_watered_at` ссылкой на удалённую запись
`Backend/controllers/plantController.js:1181-1226`; `Backend/controllers/adminManageController.js:826-869`.

`isLatestAction` определяется по **любому** последнему действию (`watered` или `skipped`). Сценарий: полив в Пн (лог), затем авто-пропуск во Вт (лог `skipped` позже по `action_at`); пользователь удаляет отметку Пн → `latestAction` — это skip, `isLatestAction=false`, пересчёт `last_watered_at` не выполняется → поле продолжает указывать на удалённую запись. **Рекомендация.** Для `last_watered_at` всегда пересчитывать по последнему **`watered`**-логу (независимо от `isLatestAction`), а `isLatestAction` использовать только для логики восстановления `next`.

### P2-10. Нет retention и нет «усталости»: рост `notifications`/`watering_logs` и вечный push-спам неактивным
`Backend/jobs/cleanExpiredTokens.js:38-103`; `Backend/jobs/reminderService.js:98-173`.

`cleanExpiredAuthData` чистит консентусы/сессии/токены/чат/ИИ-логи/визиты, но **не трогает** `notifications` и `watering_logs`. Через год на каждые 10 ежедневных «брошенных» растений — ~3650 логов + push-спам, который портит репутацию рассылки.

**Рекомендация.** Retention для `notifications` (например, 90 дней) и обсудить для логов (1–2 года); признак «активности» (последний вход/последний полив) — после 60–90 дней не шлать напоминания и не крутить авто-пропуск (или ставить растения на паузу); агрегировать auto-skip (`metadata.missed_count`).

### P2-11. `POST /water` не идемпотентен; write-эндпоинты полива без rate-limit
`Backend/controllers/plantController.js:1104-1135`; `Frontend/src/component/homePage/homePage.jsx:262-264`; `Backend/routes/plantRoutes.js:47-53`.

Двойной тап/авторетрай/два открытых таба дают два `watered`-лога на один и тот же полив (фронтовый guard `wateringId` живёт только в пределах одного инстанса React и сбрасывается при ошибке). В `plantRoutes` лимитеры есть только на ИИ-подсказки; `water/skip/delete/updateMetadata` ничем не ограничены, глобального лимитера в `index.js` нет. Аутентифицированный клиент может набить себе тысячи логов/`metadata` (общая БД страдает).

**Рекомендация.** Идемпотентность (`client_action_id` + уникальный индекс, либо «не чаще одного watered на растение в N минут»), общий `express-rate-limit` на `/api` (например, 300/15мин на IP) и отдельный на write-полив (30/мин на пользователя).

### P2-12. `/plants/schedule` раздувается: 90 дней × occurrences + полный массив фото на каждое вхождение

### P3-8. Деградация распределённого лока = дубли напоминаний
`Backend/utils/distributedLock.js:55-83`; `Backend/k8s/10-configmap.yaml:9-21`. При недоступном Redis `acquireLock` возвращает `acquired: true, degraded: true` — каждый экземпляр выполняет тик. ## 4. Что сделано хорошо (чтобы не переделывать)

* **Зональная арифметика.** `zonedDateTimeToUtc` / `zonedDayHourAfter` / `addZonedDays` / `zonedDayKey` — правильный подход вместо `setHours`; кэш `Intl.DateTimeFormat` по поясу; таймзона валидируется через `Intl` и режется по длине; дефолт Москва.
* **Изоляция данных.** Все выборки растений/логов и отметки скоупятся `user_id` в `WHERE`; `admin*` — через `requireAdmin`; `GET /plants/:id/stats` проверяет владельца перед raw-SQL. IDOR не нашёл.
* **Транзакции и блокировки.** `water/skip/delete/autoSkip` берут `SELECT ... FOR UPDATE`; бэкфилл защищён от дублей (409) — в отличие от обычной отметки.
* **Аудит и обратимость.** `metadata.prev_next_watering_at` позволяет восстановить расписание; конверсия skip→watered сохраняет исходный skip; удаление возвращает `skipped`.
* **Валидация API.** Интервал, enum времени, дни недели (уникальные, 0–6), фото строго из `/uploads/plants/<32hex>.(jpg|png|webp|heic)`, лимиты note/description/name, body 100 КБ, CORS whitelist, CSRF-защита по origin/sec-fetch-site.
* **ИИ-советник.** `parseWateringAdvice` ограничивает `1..365`, длину reason, `question/options`; дедлайн + AbortController; ретрай только на token-exhaustion; детерминированный фолбэк; кэш с single-flight; rate-limit 30/час; промпт отделяет данные пользователя от инструкций.
* **Напоминания.** `withDistributedLock` с проверкой токена в Lua и продлением TTL; per-user lock для сводки; dedupe-уникальность `(user_id, dedupe_key)`; удаление протухших push-подписок по 404/410.
* **Фронтенд.** `fetchWithTimeout` (AbortController, 15с), проверка ответов сервера на структуру, обработка 409 при повторной отметке, защита от гонки ответов ИИ-диалога (`wateringDialogSessionRef`), блокировка кнопок во время запроса, очистка таймеров.

## 7. Методика, ограничения и воспроизводимость

**Что реально проверено динамически:** импорт `Backend/utils/wateringSchedule.js` без БД и прогон сценариев (Node 24):

* базовый расчёт и склейка дат — корректно для Москвы;
* `resolvePastWatering` для просроченного слота: `actionAt = слот`, `hoursLate = 0`, `next = max(prev, слот+interval)` — воспроизведено;
* `autoSkipOverdue`: для `interval=1`, `scheduled=Пн 09:00`, `now=Вт 09:10` → `next=Ср 09:00` (двойной прыжок) — воспроизведено;
* DST: Берлин, `next=2026-03-25 09:00 CET` → occurrences и auto-skip дают `10:00 CEST` — воспроизведено;
* UTC+10: слот 19.10 09:00 = `2026-10-18T23:00Z`, `utcDayRange` = UTC-сутки 18-го → отметка того же локального дня не находится — воспроизведено;
* `parseWateringSlot`: `2026-02-31`/`не дата` → `null`; `2026-10-19T09:00` без зоны трактуется временем процесса; `3000-01-01` парсится (отсекается только проверкой «не будущее» в `water`) — воспроизведено;
* `update()` для никогда не политого: сдвиг плана на +2 дня (проба с phase) — воспроизведено.

`cd Backend; npm test` → 86 pass, 0 fail. Прод-дамп `Backend/backups/pre_auth_migration.sql` использован как иллюстрация схемы/исторических данных (дубли `watered` за 150 мс, ежедневные авто-пропуски, `hours_late` 24) — это старый снимок (2026-10-09), текущее поведение по нему не оценивалось.

**Чего не проверял (и почему):**
* Реальные Postgres/Redis/web-push/SMTP и кластер — на машине не запущены; все выводы по отказоустойчивости — из кода;
* фактическое состояние прод-БД (`next_watering_at` у живых растений, `users.timezone`, наличие старых «неверных» часов) — нет доступа;
* поведение конкретных iOS/Android push-сервисов (таймауты, 410/429);
* пуш-рассылки, почта, ИИ-бюджет — вне предмета (проверялись только в части, влияющей на полив);
* безопасность инфраструктуры/секретов — отдельный отчёт `Release-Verification-Report.md`, здесь не пересматривалась.

**Осознанно не включил в «баги»:** UTC-дедуп и `hours_late=0` при бэкфилле — это следует из удалённых тестов, т.е. было задумано. Я вынес их как «продуктовое решение требует подтверждения/пересмотра», а не как ошибку реализации.

## 8. Итог одной фразой

Ядро расчёта полива с персональными таймзонами сделано аккуратно и безопасно с точки зрения доступа к данным, но вокруг ядра накопилась **несогласованность состояний** (авто-пропуск, бэкфилл, `update`, недельный фильтр) и **недоделанная доставка уведомлений** (изоляция ошибок, таймауты, in-app экран, retention) — именно это надо закрыть до того, как продукт начнут использовать «по-настоящему» ежедневно.
